# TikTok Shop 日本站 · 智能体双件套

> 两个部署在本地的**文件型**智能体，共用一套 SKU 编码（`SZ-01 ~ SZ-18`）。
> 一个负责把产品做成**能上架的资产**，一个负责把上架后的数据变成**经营决策**。
> 本文档面向第一次接触它们的读者：读完你能知道它们各自是什么、谁在什么阶段用、以及该找哪一个。

**两个智能体都不能登录卖家后台、不抓实时数据。** 它们的输入永远是你放进文件夹的文件。

## 2. 它们怎么配合

```
[上架前]                        [上架]              [上架后]
B：TTS上品  ──── 文案/卡/详情 ────▶ 你上架 ────▶  A：TTS数据分析师
   SZ-xx.md                                   读导出表，按 SZ-xx 映射
   商品卡Prompt.md                                 ↓
   详情页Prompt.md                          哪款亏、哪款该改标题
                                                   │
                                        ◀──────────┘
                                   交回 B 改稿 → A 对比改前后点击率
```

**三个交叉一致性约定（两边必须同时维护）**

1. **SKU 编码是唯一主键**：`SZ-01 ~ SZ-18`，两个库同一套，不许另起编号。
2. **成本与规格分两处存，要一起改**：
   - A 用 `03_数据表/当前成本价格表_20261030.xlsx`（采购、物流、佣金、退货率）
   - B 用 `01_标准规范/SKU实测规格汇总.md`（材质、尺寸、重量、原产国）
   - ⚠️ 只改一边，另一边的结论就是错的。
3. **市场研究的方法论按阶段分**：B 管「上架前判断」（榜单、拆词、爆款潜力），A 管「上架后验证」（曝光→点击→加购→成交）。

## 4. 智能体 A：TTS 数据分析师

### 4.1 职责与边界

**会做**：经营诊断报告（`.md` / `.xlsx` / `.html`）· 成本价格表与物流时效表 · 单款与全店的流量、点击、加购、成交图表（PNG）· 促销保本测算 · 晚会口播稿与经营简报 · 原始数据归档与命名规范。

**不做**：不伪造销量／GMV／ROI／利润 · 不登录后台、不抓实时数据 · 不替你决定是否执行或向老板请示 · 不代上架改价发活动 · 不做法律税务合规定论 · **不把通用行业方法论当作你店铺的真实表现**。

### 4.2 工作流

| 步 | 做什么 | 交出 |
|---|---|---|
| 1 | 接数据，按 `数据上传流程.md` 归档进 `04_原始数据/00_待分析/` | 已归档原始表 |
| 2 | 核对统计规则：数据周期、SKU 映射、成本版本 | 口径与成本备注 |
| 3 | Python 计算（`05_脚本与图表/analyze_today.py`）：逐款毛利、贡献利润、点击率、转化率、日走势 | CSV / XLSX / PNG |
| 4 | 排优先级：**合规与账号安全 > 贡献利润 > 现金流 > 库存健康 > GMV > 播放量** | 经营判断 + 3 个优先动作 + 成功指标 + 复盘时间 |
| 5 | 交付到 `01_经营报告/` 或 `02_专题报告/`，结尾附晚会汇报版 | 报告文件 |

> **分支**：缺成本／运费／佣金率／退货率 → 先追问；追问不到 → 给估算口径并**标注为估算**。

### 4.4 最小使用示例

> 你：「用这份 10/13–11/02 的 product_list 看哪几款在亏钱，满 2 件 9 折和满 3 件 8 折哪个不亏」
> 它：归档 → 逐款贡献利润核算 → 标亏损与滞销 → 促销保本测算 → 交出 Excel 测算表 + Markdown 结论 + 3 个可执行动作

## 5. 智能体 B：TTS 上品

### 5.1 职责与边界

**会做**：商品事实核验与台账（每款一份 `SZ-xx.md`）· 日文 Listing 文案（标题 / 5 卖点 / 5 组搜索词 / 双层详情 / 11 字段属性表）· 合规分级审核（BLOCK／WARN／INFO）· 商品卡 7 卡位视觉企划与 Prompt · 详情页主海报企划 · FastMoss 榜单抓取与拆词 · 批量与建档 · 文档产出（xlsx/docx/pptx/pdf）· 生图（**默认关闭**）。

**不做**：不替你决定经营动作（选品/定价/库存/投放，只给可比较选项）· **不编事实**（缺实测一律 `【待確認】`）· 不写医疗功效与绝对化 · 不登录后台 · **不把 `0 BLOCK` 说成「可以上架」** · 不擅自回溯修改已归档历史包。

### 5.2 工作流

| 步 | 做什么 | 交出 |
|---|---|---|
| 1 | 判定模式（文案／卡／详情／审核／批量／全套） | 一句范围确认：做哪几款、哪一层、动哪些文件 |
| 2 | **事实对齐（必做，会打断）**：对照 11 个必填字段 | 事实状态表（已确认／待确认） |
| 3 | 先查三套现行规范，确认卡位数量、标题字数、颜色规则、配图张数 | 本轮硬约束清单（内部） |
| 4 | 生产：写文案／写 Prompt／拆词 | 落在 `SZ-xx/` 下，固定卡位命名 |
| 5 | 自动校验循环：`文案合规自检.py`，必要跑 `建档校验.py` 与回归测试 | BLOCK／WARN／INFO 三级日志 |
| 6 | 交付：文件链接 + 改了什么 + 仍需你拍板的事实缺口 | 文件卡片 + 一句结论 |
| 7 | 沉淀：新口径写进跨会话记忆，旧说法标历史快照 | 更新后的记忆索引 |

> **分支 1**：缺关键事实（材质/尺寸/是否含袋/每袋数量）→ 标 `【待確認】` 继续做「待确认版」，不停工，但不当成确定事实。
> **分支 2**：实物图缺失或角度不足 → 先给《素材补充清单》，未知外观用占位符，不臆造。
> **分支 3**：出现 BLOCK → 改完重跑；只剩 WARN → 继续，但 WARN 写进交付说明，不隐瞒。

## 8. 已知限制（合并版）

**数据与事实**
- 两者**都没有后台实时连接**，全部结论依赖你放进文件夹的文件；表缺字段时只能估算并标注，可信度随之下降。
- A 的口径陷阱：周五数据按周期起始日命名，滚动 7 天、7 天累计与单日不能混用，历史快照不能与最新综合表相加。**你给错文件它就算错。**
- A 的费率陷阱：平台费率、佣金、退货率沿用旧值，保本价与贡献利润直接偏差，敏感结论需你复核。
- B 的事实底线：没有实测数据一律 `【待確認】`，**「待确认版」文案不能直接上架**。反过来——**它写得越顺、而你没给依据，越可能是在套模板，请抽查。**
- B 的抓取口径：按「近 7 天销量」排序，`region=JP` **包含跨境店**，不是日本本土店全貌。

**工具**
- `关键词分析.py` 依赖 `janome`，当前环境未装，需先装依赖。
- 生图模型不可靠：曾出现多指、指甲走形、日文字写歪，故规范强制「零文字底图 + 后期叠字」。**默认策略是只交 Prompt，你自行生图。**
- `GPT Image 2.5 Flare` 不在当前可选模型列表；`Nano Banana 2` 这个确切型号名未在上下文中核实到，只能确认接的是 Gemini 图像入口。

**判定性质**
- B 的合规判定是**正则 + 人工规则库**，不是法律意见；`0 BLOCK` 只表示本次未命中阻断规则，**不代表平台一定过审，也不代表事实已核验完**。
- A 的促销、定价、达人佣金只是**方案**，报不报批、上不上线由你决定。
- TikTok 类 Skill 给的是**通用最佳实践**，不代表你店铺的真实表现，不能当数据结论引用。

**已知内部冲突（按现行规范执行）**
- B 的项目 Instructions 里还留着四套微缩预设（WARM-SUNLIGHT 等）与四季节日插槽，但 2026-11-02 的商品卡规范已将其作废、改为货架逻辑。**遇未覆盖情形它会停下来问你，不会自己挑一个。**
- B 的回归测试有 **1 项长期红**（断言 SZ-17 标题来源为章节，实际已改成机器可读区），属测试基线滞后，不影响交付。
